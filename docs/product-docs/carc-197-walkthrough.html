CARC 197 — branches, not a plan

An authorization denial has a small number of ways it can be true, and they are known in advance. So the machine does not draft a sequence of steps — it evaluates the whole branch set at once and asks which one the evidence supports.

The run

Playbook — owns the branch set

the scenarios are authored, not discovered

CARC 197 has five branches. They exist before the claim arrives, they are the same for every 197, and nothing outside this set may be executed. That constraint is what makes the Judge's job possible: it validates a branch against its stated precondition rather than grading free prose.

Drafter — instantiates and weights

against THIS claim, using priors — and it may not add a sixth branch

For each branch: does it plausibly apply here, and what is the prior probability given payer, service and denial history? The Drafter's contribution is the reading of the case, not the invention of options. If it proposes something the playbook lacks, that is a playbook gap to file — not a step to run.

Assembler — the data each branch would need

per branch, the required items and where each would come from

B1 needs an auth record. B3 needs admission type and presenting diagnosis. This is what turns a scenario into something answerable — and it is computed per branch, in parallel, not as a sequence.

Judge — accuracy per branch

two independent questions, and they must not be collapsed

Is the branch stated accurately — does the playbook's precondition match what the rulebook actually says? And is the evidence real — does the cited record support it? A branch can be accurately stated and unproven (B2), or well-evidenced and refuted (B4).

Arbiter — which can execute, and what state we move to

the only actor that reads the weights

Executable now → run it. Accurate but unproven → dispatch to fetch the missing evidence. Refuted → close the branch and record why. Nothing executable and nothing fetchable → bring it forth to a human, with the branch table as the reason.

The part that makes it a machine rather than a report

A case does not finish in one pass. It moves through states, and each state change re-enters the loop with everything already established.

1 · state changesthe auth record comes back, or the Locator finds the retro policy
2 · case returns to Drafterwith the claim, the branch table, and every prior verdict — not a fresh start
3 · re-weightbranches close, priors shift, one may become executable that was not
4 · Arbiter moves stateexecute, dispatch again, or bring it forth

So the Drafter is asked the same question repeatedly against a growing evidence set, and the branch table is the memory. That is why the branches must be authored: a set that changed shape every pass could not accumulate anything.

Four boundaries this makes sharp

The playbook owns the branches; chat may not add one. An invented scenario has nothing to validate against, so the Judge would have to grade prose and the Arbiter would execute on a model's suggestion. A proposal outside the set is a gap to file against the playbook.
Priors reach the Arbiter, never the Judge. A 0.34 prior says nothing about whether B1 is true. If the Judge saw it, a well-scored branch would start to look verified. It belongs where it does real work: ordering what to try, and deciding whether the effort is worth the remaining days.
"Accurate" and "proven" are separate verdicts. B2 is stated correctly and cannot be verified because we do not hold the retro-auth policy. Collapsing those into one column would either execute an unproven branch or discard a good one — and the second failure is invisible.
A branch that cannot be evaluated is a sourcing gap with a deadline. B2 is blocked on a document, and there are 12 days left. That is not a research task queued behind others — the clock ranks it, and the Arbiter is the only actor that can see both.
