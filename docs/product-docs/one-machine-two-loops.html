One machine, two instantiations

Sourcing a fact and adjudicating a denial ran as separate builds. They are the same machine. Formalising that is worth doing carefully, because the differences are not a list — they descend from a single choice.

Both loops do one thing: reduce a set of candidates to what the evidence supports.

In the fact loop the candidates are the field values an answer proposes. In the denial loop they are the branches a playbook enumerates. Everything else — the roles, the contracts, the gates, the re-entry — is identical, because that reduction is the same operation either way.

The invariants — true in both, and load-bearing

  • One unit, one evidencea field or a branch stands on its own quote. No unit borrows another's grounding.
  • Judge may not actreject or abstain only. A judge that can repair is a second drafter with a veto.
  • Abstain ≠ passabsence of a check is reported as absence, never as approval.
  • Priors stop at the Arbitera weight says nothing about whether something is true. A judge that sees one starts treating favoured units as verified.
  • The loop never repairsit names the state and dispatches. Repair belongs to whoever owns that capability.
  • Source by id, never by namea name cannot be joined back. This is how a store ends up with facts it cannot trace.
  • Re-entry carries everythinga state change returns the case with every prior verdict. Nothing is re-argued without new evidence.
  • The caller sets the barcompleteness or confidence, and the threshold. Same machine, one line of policy apart.

The one difference everything else descends from

Candidates are either generated or enumerated. That single fact decides the rest of the table below — which is why it is worth stating on its own rather than as row one of ten.

When candidates are generated, only each candidate can be checked; the set itself is unbounded and unvalidatable. When they are enumerated, the set is an artifact with an author and a version — so "is this candidate accurately stated" becomes a question with an answer, and a Playbook actor becomes possible.

Executor is the actor I had missing. In the fact loop, committing the record IS the action, so Recorder covers both. In the denial loop they come apart: something files the dispute, and something else writes down what happened. Collapsing them means the record of an action is produced by the thing that took it — which is exactly the separation the Judge and Recorder split exists to preserve elsewhere.

What the formalisation predicts

A framing earns its keep by saying something that was not put into it. Three that follow:

A fact loop given a closed candidate set gains the accuracy check for free. Ask "is the limit period one of: day, week, month, quarter, state fiscal year, lifetime" and the period becomes enumerated — so the Judge can test whether the enumeration matches the rulebook, not merely whether a value is quoted. Several fact-loop failures today were values that were quoted correctly and belonged to no legitimate category.
Any loop whose output becomes executable inherits the satisfiability gate. The moment a sourced fact is used to auto-file something, "is it grounded" stops being sufficient and "can it be acted on now" becomes a gate. That is a property of the consumer, not of the fact — so it belongs in the Requester's bar, next to completeness and confidence.
The Playbook is a corpus with a version, so it has the same failure modes. A branch missing from the playbook is invisible in exactly the way a document missing from the corpus is invisible: nothing reports it, the machine simply never considers it. So the denial loop needs its own playbook_gap class, filed the same way not_in_corpus is — which is what the Drafter's forbidden sixth branch becomes.

Where they genuinely diverge, and it is not fixable

An assertion is inert. A wrong record sits until an audit finds it, and the audit is cheap — one of the eleven judge skills found eight bad fields in an afternoon. An action is not inert. A dispute filed on an unproven branch consumes an appeal level that does not come back, and no later audit undoes it.

So the two loops can share every contract and must not share a default. The fact loop should prefer attempting — a rejected field costs a turn. The denial loop should prefer abstaining — an unproven branch costs a right. Same machine, opposite thumb on the scale, and the Requester's bar is where that thumb belongs.

Both loops are running. The fact loop has 11 judge skills, 7 gap classes and a repair queue against the live corpus; the denial loop is designed and drawn, not built. This page is the contract they would share.
