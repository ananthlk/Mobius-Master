The machine, both loops

One pipeline, and one loop. What looked like two machines is this machine run at two levels — once about a class, whose answer is kept, and then about each instance that arrives.

◆fact loop — sourcing a value ◆denial loop — adjudicating a branch

What the picture is asserting

An earlier version of this drawing showed the Playbook as a second input and called it the fork between two loops. That was wrong, and the correction is the whole point of this page.

The spine never changes. Propose, type, test, decide, act, record. Swap the unit from a field to a branch and every box keeps its contract — which is why these were the same build all along and were written as two.
The Playbook is this loop’s own earlier output. It is not a second kind of input. Ask “what are the ways a CARC 197 can be true?” and that is a question with candidates, evidence and verdicts like any other — the same pipeline answers it, and the Recorder keeps the answer. A case that arrives with no playbook does not need a different machine; its first pass produces one.
So the difference is caching, not architecture. Enumerated means the class-level question was already asked and its answer is being reused. Generated means it has not been asked yet. That is an operational choice — determinism and cost against adaptability — and it is why the Judge can ask whether a branch is accurately stated: the branch was itself sourced once, so it has a quote to be checked against.
Which makes the Playbook a fact store, with a fact store’s problems. It can be stale, it can be wrong, and a branch missing from it is invisible in exactly the way a document missing from the corpus is invisible. So it needs the same treatment as anything else this loop produces: a version, evidence per branch, and re-verification. A playbook nobody re-sources is a certified store nobody audits.
The priors rail crosses out at the Judge. Weights reach the Drafter, to read the case, and the Arbiter, to rank what to try. They must not reach the Judge: a favoured candidate under a Judge that knows it is favoured turns “partial” into “proven”. Drawn as a broken line because it is a rule, not a wire.
The Arbiter is the only box with a heavier border. It is the one actor that sees verdicts, weights and the clock together, and the only one permitted to change state. Everything above it produces evidence; everything below it acts.
Executor's two rows are not a list, they are a boundary. Inward skills change our own state and a failure costs a dispatch. Outward skills change the world's and some cannot be undone. Same actor, same dispatch — different gate, and the caller's bar is what sets it.
Re-entry returns to the Drafter, not to the Requester. A state change re-asks the same question against a larger evidence set, carrying every prior verdict. That is what makes it a machine rather than repeated prompting — closures accumulate and are not re-argued without new evidence.
The loop is built and running against the live corpus at instance level — 11 judge skills, 7 gap classes, a repair queue. It has not yet been pointed at a class-level question, which is the only thing standing between it and producing a playbook rather than consuming one.
