## Real crash bug found during DB's code review (Retriever, 2026-07-24) — FIXED

## New requirement (2026-07-24): force a retry on technical failures — RESOLVED, 3-layer design confirmed by Retriever

Ananth's standing principle: "ask once and get the answer" — try our best for first-pass resolution rather than degrading immediately on a technical failure. This is a whole-pipeline concern; **Retriever ruled on the full layering** (coordinated, not decided unilaterally):
- **Per-rung** (already built, `_try_strategy`): one filler technically failing advances to the next rung in that slot's ladder, same query.
- **Whole-loop** (Retriever just built this): anything escaping per-rung handling — the entire pipeline retries once.
- **Per-helper** (this module, finest scope, retry first): `_resolve_document_names`/`_complete_neighbors` retry once (`_MAX_TECHNICAL_RETRIES = 1`) before escalating.

**Correction applied after Retriever's ruling**: the initial implementation caught the exhausted-retry failure and returned a degraded result with a soft error flag (`document_name_lookup_errored`/`neighbor_completion_errored_slots` telemetry fields). Retriever's ruling was explicit: a failure surviving its own local retry must **RE-RAISE**, not degrade silently — otherwise the whole-loop retry never gets a chance to recover a systemic failure (e.g. a genuinely broken DB connection), and Synthesis would quietly return a degraded result query after query instead. **Fixed**: both functions now re-raise after `_MAX_TECHNICAL_RETRIES` is exhausted; `compile_synthesis` does not catch this, so the exception propagates to the orchestrator's whole-loop retry. The two soft-error telemetry fields were **removed** as dead code under this design — they could never be populated in any successfully-returned `SynthesisResult` (if that path is hit, `compile_synthesis` raises instead of returning). 4 tests updated to assert re-raise (`pytest.raises`) instead of a soft-flagged degraded result.
