# Forced-Filler Bank Grading Report (Eval)

**Source artifact:** `mobius-rag/eval/artifacts/forced_filler_bank_run.json` — 22/22 queries, all 5 real strategies (a/b/c/d/s) forced individually, Gate+Pool shared once per query (corrected re-run). Real chunks, real latency, real error state per Retriever's non-negotiable requirement — not a summary.

**Grading methodology:** per (query, strategy), `recall` = fraction of that query's `must_facts` findable in the strategy's full returned chunk text (not just occupancy/chunk-count — a slot full of irrelevant or junk content scores 0 regardless of occupancy, same standard applied to Filler b's earlier junk-boilerplate finding). `forbidden_facts` presence would be an automatic precision failure; none were found stated as fact in any strategy's output across the bank (both a strength of the corpus and a sign these queries aren't adversarial enough to stress precision — worth noting for future bank expansion). Facts graded by distinctive-token presence (numbers, codes, key terms) against full chunk text, spot-checked by direct reading against the artifact's actual content for every row below — not scored blind.

**Oracle-over-strategies (best single-strategy recall per query, i.e. "if Router always picked perfectly"): 0.894 mean, 19/22 queries at 1.00.** Distinct from Pool's previously-documented `oracle_recall` (0.84, union-of-all-candidates ceiling before any strategy choice) — this is a strategy-selection ceiling, not a pool-content ceiling. cmhc016/cmhc021 (see corrected notes below — these are Shape-layer CLARIFY short-circuits, not corpus gaps, and never reach any filler in the live pipeline) score zero regardless of strategy in this forced-standalone harness and drag this number down; excluding them, the oracle over the other 20 queries is higher still. High because a and d individually score strong (.855 / .879) with only partially-overlapping misses — picking the right one per query closes most of the remaining gap.

**Interpretation, not just numbers:**

- **d edges out a on raw recall (.879 vs .855), at roughly 16-20x the latency.** d is a genuinely strong strategy on this bank when it fires, but its cost profile (10-21s vs a's sub-second) confirms the fleet's own "recall-of-last-resort" framing for d — it's the right fallback, not a default.
  - **AUTHORITY CAVEAT (Ananth, 2026-07-23, supersedes any "promote d" reading of the recall/payload numbers):** d's recall lead is real and holds under strict grading (0.542 vs a/b's ~0.15), and its per-chunk payload is the smallest verified (500 vs a/b's uncapped corpus chunks) — but recall is NOT fungible in this domain. A corpus chunk from an ingested payor manual is *citable evidence* in a claims dispute; a web extract stating the same fact accurately is *not citable to the payor*. So d's answer-value for required, payor-facing `direct_answer` slots is capped by non-citability regardless of recall/cost. The correct strategic question is NOT "is d's recall real" (probably yes) but "when is non-citable recall worth anything" — and for compliance answers the honest answer is "as a pointer/scout, not as primary evidence." d's correct roles stay: `external_context` slots (already d-only by eligibility), genuine last-resort when citable strategies fail, and a possible future scout pattern (web fact → re-query corpus for the citable source). The current code already encodes this (d last in priority order, external_context d-only) — nothing to change in code; this caveat exists so the eventual LLM-judge regrade does NOT conclude "promote d for direct answers" from the recall/payload numbers alone without the authority axis in frame.
- **a is the clear efficient baseline** — near-d recall at near-zero marginal cost, exactly matching Retriever's earlier real-latency finding that a/b ride Pool's already-fetched candidates for free while c/d/s each pay their own external-call cost.
- **b is bimodal by design now, not by defect** — 13/22 perfect matches a exactly, 8/22 are honest zeros from the same vector-arm poisoning issue already found and partially fixed (length-floor + dedup). This is the expected shape post-fix: real recall where the vector arm has real content, honest silence where it doesn't, no in-between fabrication.
- **c is weak across the board (0.166 mean), not just occasionally** — 14/22 zero-occupancy, and the two non-zero cases that scored well (cmhc011 at 1.00) show it's *capable*, just unreliable, and its slowest call (43.98s on cmhc020) is a real latency risk if it were ever a synchronous rung with a tight speed_budget. Also observed a repeatable pattern: c converges on the *same* single citation (the EDI/clearinghouse chunk) across multiple unrelated queries (cmhc001, cmhc007, cmhc009) — worth Filler c's attention as a possible retrieval-anchoring bug, not just "the LLM didn't find anything."
- **s correctly scores 0.000 on this bank, and that's not a failure** — s is a narrow structured-fact lookup (Payer ID, plan codes), and none of these 22 queries ask questions s's fact store actually covers. This bank isn't the right instrument for judging s's real precision/recall — a payor-tag-relevant query bank would be needed for that (ties to the tag-gating fix already shipped in Router, which correctly restricts s's eligibility to `j:payor.*`-tagged slots).
- **CORRECTED (Retriever, 2026-07-23): cmhc016/cmhc021 are NOT corpus gaps.** Both hit Gate `contour=UNDERSPECIFIED` → Reformat `posture=CLARIFY` → zero slots, so in the live pipeline no filler ever runs for these two queries at all — the ~600-700ms "fast" reaction time on both is Gate+Reformat+Structure only, not "d searched and found nothing" (see the corrected bimodal note below). This forced-standalone harness bypasses that real dispatch gate and shows what fillers WOULD return if invoked, which isn't representative. Route the real open question (is UNDERSPECIFIED/CLARIFY the right classification for these two queries?) to Gate/Reformat's owner, not Curation.
- **One real, unresolved citation-trust instance surfaced in this run** (cmhc009's `d` chunk in the `Fact: | Value: | Source: Official | Confidence: high` format) — this is the exact pattern flagged earlier to Chat for the `ai_extracted` source-type/grounding-badge design; this run gives a second concrete example to fold into that post-v1 work.
- **d's repeated-identical-chunk issue** (cmhc010, cmhc013 — 3 byte-identical chunks in the top-3) suggests Filler d may need the same dedup treatment already shipped for Filler b — flagging as a real, scoped follow-up, not assumed to already be covered.
