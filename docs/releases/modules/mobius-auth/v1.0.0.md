## What this module is
mobius-auth is `@mobius/auth`, the shared front-end auth package used by both mobius-chat (web) and the mobius-os extension. It ships one AuthService plus the login/signup/account modal, preferences modal, and user menu, so both surfaces run the same code and the same UX. It is a client library — it calls an auth API, it does not implement one.

## What v1.0.0 establishes
- A single `AuthService` over a pluggable storage adapter, so web (`localStorageAdapter`) and extension (`createChromeStorageAdapter`, proxied via the background page) share one implementation.
- The full credential surface: login, registration, email check, token refresh, logout, and profile fetch, with an event callback channel for consumers.
- Google sign-in via Google Identity Services — the client loads GIS, obtains an ID token, and the backend verifies it against Google's JWKS.
- The UI kit consumers mount directly: `createAuthModal`, `createPreferencesModal`, `createUserMenu`, plus exported style strings (`AUTH_STYLES`, `PREFERENCES_MODAL_STYLES`) and a toast helper.
- A typed user model — `UserProfile` and `UserPreferences` covering greeting name, timezone, locale, onboarding state, activities, tone, AI experience level, and per-category autonomy settings.
- Onboarding flow: a welcome panel that routes into preferences via `onOpenPreferences`, with a set-up-preferences CTA.
- Tour anchors (`data-tour-id`) on the auth surfaces, making this package addressable by the interact/tour machinery.

## Contracts other modules depend on
- **Package identity:** `@mobius/auth`, consumed as a file dependency (`npm install file:../mobius-auth`); entry points `dist/index.js` (cjs), `dist/index.mjs` (esm), `dist/index.d.ts`.
- **Public exports:** `createAuthService`, `AuthService`, `localStorageAdapter`, `createChromeStorageAdapter`, `STORAGE_KEYS`, `PERSISTENT_KEYS`, `IStorageAdapter`, `createAuthModal`, `createPreferencesModal`, `createUserMenu`, `AUTH_STYLES`, `PREFERENCES_MODAL_STYLES`, `showToast`, `getGoogleIdToken`, and everything in `./types`.
- **Backend endpoints called**, relative to the configured `apiBase`: `POST /auth/login`, `POST /auth/register`, `POST /auth/google`, `POST /auth/refresh`, `POST /auth/logout`, `GET /auth/me`, `POST /auth/check-email`. Renaming or reshaping any of these breaks every consumer of this package.
- **Type contract:** `UserProfile` (user_id, tenant_id, greeting_name, timezone, locale, is_onboarded, activities, tone, plus optional org_memberships) and `UserPreferences`; `AuthTokens` as access_token / refresh_token / expires_in.
- **DOM anchors:** `data-tour-id` values `modal-auth`, `menu-preferences`, `modal-preferences`, `menu-sign-in` are depended on by tour scripts outside this repo.
- **External dependency:** Google Identity Services loaded from `https://accounts.google.com/gsi/client`; a Google client ID must be supplied by the host app.

## Known gaps carried into v1.0.0
- There is no test suite in the repo — no test directory, no test script in `package.json`. Correctness is verified only by running the consuming apps.
- `dist/` is committed to the repository alongside `src/`, so a stale build can ship if a consumer installs without rebuilding.
- The package is distributed by local file path rather than a registry, so consumers have no version pinning and no way to detect a breaking change except by rebuilding.
- Token storage is delegated entirely to the host's storage adapter (localStorage in web); the package makes no claim about where refresh tokens end up or how they are protected.
- The 2026-07-08 history includes a merge from a detached line ("Merge preference fixes + tour anchors from detached line"), so the pre-v1 lineage of the preferences work is not linear.
