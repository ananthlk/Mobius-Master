# product-awareness v1.0.0

**Commit:** `44d14cd` · **Branch:** `main` · **History:** 1 commit (module carve-out), 2026-09-07

## What this module is
product-awareness answers "how do I use Mobius?" from the product documentation. It owns its own corpus (`product_docs`), its own embedder and its own vector store, and imports no other Mobius module's internals. Every question it cannot answer is turned into tracked documentation debt via a best-effort write to the feedback agent's `product_feedback` table — the docs loop.

## What v1.0.0 establishes
- A complete offline-to-production pipeline: markdown manuals are chunked by `##` H2 section into inspectable `corpus/chunks/<module>.jsonl`, then embedded into a vector store, driven by a `cli` with `ingest | search | stats | calibrate`.
- Deliberately lazy retrieval — vector-only, no BM25, rerank, strategy layer or lexicon — on the grounds that product docs are small and curated.
- Pluggable stores and embedders: pgvector on Cloud SQL with the module's own `product_docs_embeddings` table plus Vertex `gemini-embedding-001` pinned to 1536 dimensions in production; numpy cosine plus a local TF-hash embedder offline, so the pipeline runs with no credentials.
- A three-outcome disambiguation keyed off one threshold: `s_top < τ_gap` gives `docs_gap`; `s_top >= τ_gap` on a chunk flagged `status=planned` gives `feature_request`; otherwise `answer`. A single constant (`PRODUCT_HELP_TAU_GAP`) governs both "cannot answer" and "fire a gap", so the two cannot drift.
- A `status=planned` reality gate set at chunk time from the `## Not yet available (planned)` section — the mechanism that separates missing documentation from a missing feature.
- A stateless FastAPI retrieval service: `/search` returns the outcome and a `gap` payload but never writes it; the chat-side handler files the gap in-process, keeping the write on the chat side per the contract.
- A `/doc` endpoint that reconstructs a full doc-reader envelope (TOC plus sections) from the shipped chunks, so product docs render in chat's document panel without living in `rag.documents`.
- A read-only backlog view (`/backlog`) over the feedback agent's views, plus served static surfaces `/schematic` and `/welcome-preview`.
- Cloud Run packaging: the image ships only `product_awareness` and `corpus/chunks`; embedding into pgvector is a separate ingest job, and the service itself only reads.

## Notable in the run-up
This module has exactly one commit — the carve-out — so the capability, not the history, is the record. What the carved-out code already contains:
- The chunker excludes author meta (`Doc-readiness notes`) so it is never ingested, and applies a `MAX_CHUNK_CHARS` bound.
- `config.DOC_META` maps 14 source manuals to module slug, audience (`user` / `dev` / `mixed`) and an `in_scope` flag, which `/search` can filter on via `audience`, `module` and `in_scope_only`.
- `config.DEMOS` attaches published mobius-interact demo scripts to (module, section) pairs so chat can render a "Show me" chip on an answer.
- `/search` returns `sources_count` specifically so chat's react loop can emit concrete progress text without recounting client-side.
- The gap writer is wrapped end to end: when it cannot import chat's storage, or the insert raises, it logs and returns `None`. Filing a gap can never break the answer path.
- `deploy/dev.env` records a two-sided τ_gap probe run on live Vertex plus pgvector (in-corpus p10 = 0.602, out-corpus p90 = 0.486) and pins the deployed value at 0.544.

## Contracts other modules depend on
- `POST /search` (port 8070 locally; `$PORT`, 8080, on Cloud Run) — request `{query, k, audience, module, in_scope_only}`; response `{outcome, query, s_top, tau_gap, text, sources, sources_count, module, gap}` where `outcome` is one of `answer | docs_gap | feature_request` and `gap` is null or `{category, module, verbatim, summary}`. mobius-chat's `product_help_search` builtin calls this via `CHAT_SKILLS_PRODUCT_HELP_SEARCH_URL`.
- `POST /doc` — `{document_id, view}` where `document_id` is `product-docs:<module>`; chat's `doc_reader` proxy routes those ids here and receives the doc-reader envelope shape (`envelope_id`, `document_id`, `toc`, `sections`, `provenance`, `rendering_hints`).
- Skill name `product_help_search`, registered chat-side as a `SkillSpec` plus manifest registry block.
- Cross-module write seam: `docs_gap` / `feature_request` rows into the feedback agent's `product_feedback` table via `insert_open_feedback(trigger="auto_harvest", category, area_tags=[module], verbatim, summary, routed_to, …)`. This is the module's only cross-module touch — see `/Users/ananth/Mobius/docs/product-awareness-feedback-contract.md`.
- Read-only consumer of the feedback agent's backlog views (`module`, count column, `sample_verbatims`) from the `mobius_chat` database, surfaced at `GET /backlog`.
- Store: pgvector table `product_docs_embeddings` (`PRODUCT_DOCS_TABLE`) on `mobius_rag`; collection name `product_docs`.
- Config seams other modules or deploys set: `PRODUCT_HELP_TAU_GAP`, `PRODUCT_DOCS_STORE`, `PRODUCT_DOCS_EMBEDDER`, `PRODUCT_DOCS_DATABASE_URL`, `PRODUCT_DOCS_EMBED_MODEL`, `PRODUCT_DOCS_EMBED_DIM`.
- `GET /health`, `GET /schematic`, `GET /welcome-preview`.

## Known gaps carried into v1.0.0
- τ_gap is not calibrated on the production embedder according to the module's own README: the 0.35 code default is a provisional cosine start, and the offline TF-hash stand-in has no reliable semantic separation (in-corpus and out-of-corpus score distributions overlap), so it validates plumbing only, not retrieval quality. `deploy/dev.env` carries a calibrated 0.544, which means the code default and the module documentation disagree with the deploy config; anything run outside that dev deployment uses the uncalibrated 0.35.
- The README and `config.py` still describe OpenAI as the embedder in places (`PRODUCT_DOCS_EMBEDDER=auto|vertex|openai|local`, "calibrate on the OpenAI embedder") while production is Vertex `gemini-embedding-001` — stale documentation on the load-bearing threshold decision.
- Chat wiring is described in the README as "the next step" even though the chat side already sets `CHAT_SKILLS_PRODUCT_HELP_SEARCH_URL`; the README also names the env var `CHAT_SKILLS_PRODUCT_HELP_URL`, which does not exist in mobius-chat.
- Gap filing is best-effort by design: outside the chat import path there is no DB, so gaps are logged and dropped. A silent write failure produces no user-visible or operator-visible signal beyond a log line.
- `/backlog` swallows every exception from the feedback views and returns an empty result, so an absent view and a broken connection are indistinguishable.
- Test coverage is a single file, `tests/test_pipeline.py`, run against the offline numpy plus TF-hash path — the production pgvector and Vertex path is not covered by tests.
