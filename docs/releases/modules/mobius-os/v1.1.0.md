# mobius-os v1.1.0

**Commit:** `a5696f4` · **Branch:** `main` · **History:** 68 commits, 2026-01-14 → 2026-08-25

## What this module is
mobius-os is the browser-extension surface of Mobius plus the Flask backend that serves it. The extension runs alongside a user's existing EMR, RCM, or email tab and offers two shapes — a small always-on Mini widget and an expandable Sidecar panel — that detect what page the user is on and propose actions. The backend holds the resolution/plan state, alerts, mock EMR and CRM surfaces used for demo and development, and a skills proxy to the rest of the fleet.

## What v1.1.0 establishes
- Supersedes the stale `v1.0.0` tag, which points at a January 2026 commit roughly 60 commits behind HEAD and predates all of the auth, chat, and envelope work below. Treat v1.1.0 as the first tag that describes the module as it actually stands.
- The two-mode extension surface: Mini widget (allowlist-gated, expand-to-sidebar, patient context detection, Needs Attention workflow) and Sidecar (factor cards, remedies, view preferences, answer persistence across reloads).
- A Flask backend with ten registered blueprints under `/api/v1/*` plus mock EMR and CRM surfaces, backed by SQLAlchemy models and Alembic migrations.
- Centralized theming: a theme and density system for Mini and Sidecar, and a sustained conversion of inline component styles to CSS variables aligned with the Mobius design tokens.
- Federated identity: the extension signs in through the shared mobius-user service rather than holding its own account system; the backend also carries a Google sign-in route issuing JWTs from `JWT_SECRET`.
- Chat inside the extension: QuickChat wired to the shared mobius-chat service as a no-PHI assistant, with consent-gated page context and a local, zero-egress PHI screen run before anything is sent.
- A mode-aware envelope engine — a client-side registry mapping detected surface × role to a proposed action set, shaped so it can later be served from a backend manifest without changing consumers.
- Deployment infrastructure: Cloud Build config, `deploy.sh`, a `mobius-os-dev` Cloud Run target, and seed scripts treated as a batch-job data contract.

## Contracts other modules depend on
- **Backend HTTP surface** (blueprint prefixes registered in `backend/server.py`): `/api/v1/auth/*` (`register`, `google`, `login`, `refresh`, `logout`, `me`, `onboarding`, `check-email`, `activities`), `/api/v1/resolution/*` (`plan/patient/<id>`, `plan/<id>`, `my-tasks`, `answer`, `note`, `step`, `reassign`, `resolve`, `escalate`, `skip`), `/api/v1/sidecar/*` and `/api/v1/user/alerts*`, `/api/v1/skills/corpus_search`, `/api/v1/modes/chat/message`, `/api/v1/mini/*` (`status`, `ack`, `note`, `issue`, `patient/search`), `/api/v1/context/*` (`detect`, `config`, `lookup`), and the demo surfaces `/mock-emr/*` and `/mock-crm/*`.
- **Extension manifest** — `extension/manifest.json` plus the built `extension-prod/` bundle; host permissions and the allowlist define which pages Mini appears on.
- **Persistence** — SQLAlchemy models under `backend/app/models/` (patient, plan/resolution, assignment, evidence, event_log, invocation, sidecar, tenant, user_issue, mock_emr, scheduling, billing, intake) with Alembic migrations in `backend/migrations/`.
- **Upstream services** — mobius-user for sign-in, mobius-chat for QuickChat, the RAG skill endpoint behind `RAG_API_URL` for `corpus_search`, and the email skill behind `MOBIUS_EMAIL_SKILL_URL`.
- **Client-side envelope registry shape** — `Envelope` / `EnvelopeAction` types in `extension/src/services/envelopes.ts`, deliberately mirroring the shape a server-served detection config would return (`fetchDetectionConfig`).

## Known gaps carried into v1.1.0
- The envelope registry is client-side only; the backend manifest it was shaped for does not exist yet, so any envelope change ships as an extension rebuild.
- Some envelope actions are `kind: 'preview'` — the surface is recognized but no flow is built behind them (`find_email`, `collate`).
- The local PHI screen is explicitly not authoritative and cannot detect unlabeled person names; enforcement still depends on mobius-chat's server-side classifier gate after consent.
- `mock_emr` and `mock_crm` are demo scaffolding registered in the same app as real routes; there is no separation preventing them from being served in a deployed environment.
- Two sign-in paths coexist — the extension's mobius-user flow and the backend's own `/api/v1/auth/google` + local JWT issuance — and the module does not declare which is authoritative.
- The published `v1.0.0` tag remains wrong and stale; nothing in this release re-points it.
