# mobius-dbt v1.0.0

**Commit:** `400b166` · **Branch:** `main` · **History:** 17 commits, 2026-02-02 → 2026-07-08

## What this module is
mobius-dbt is the dbt-managed BigQuery datalake for Mobius. It lands source data into BigQuery, builds contracted marts with dbt, and syncs the results outbound — RAG embeddings to Chat's Postgres and Vertex AI Vector Search, analytical marts to downstream consumers. It also ships a small FastAPI job UI for triggering and inspecting runs.

## What v1.0.0 establishes
- The landing → mart → sync pipeline: `scripts/ingest_rag_to_landing.py` copies RAG's `rag_published_embeddings` into BigQuery `landing_rag`, dbt builds the mart, and `scripts/sync_mart_to_chat.py` pushes metadata to Chat Postgres and vectors to Vertex.
- A contracted `chat_rag` mart (`published_rag_embeddings`, plus `llm_calls`, `llm_config_versions`, `phi_audit_log`) with dbt contracts and uniqueness/not-null tests.
- The FL Medicaid NPI mart family — NPPES, taxonomy, address, and roster reconciliation models, including the B0–B6 step models and the provider readiness report pipeline.
- A financial benchmarking mart: HCPCS rate benchmarks and trends, org and service-line KPIs, peer distributions, leakage, and assessed benchmarks (v2 models alongside the originals).
- A strategy mart for market analysis: market and geo monthlies, micro-market concentration, taxonomy churn, and displacement targets/feature matrix.
- A BH roster mart layered on medicaid_npi — roster readiness, sites, revenue impact, and ghost-billing detection for FL.
- Operational plumbing: a job UI with record counts, `dbtRunner` in-process execution, parallel BigQuery environments (dev/prod dataset env vars), incremental mart and sync behavior, and cost tagging that keeps expensive models out of CI.

## Contracts other modules depend on
- **Inbound from RAG:** reads `rag_published_embeddings` from RAG's PostgreSQL (contract lives in the RAG repo, `docs/CONTRACT_DBT_RAG.md` §3). Read-only; RAG owns that database.
- **BigQuery landing:** dataset `landing_rag`, table `rag_published_embeddings`, with `embedding` as `ARRAY<FLOAT64>` of length 1536.
- **Mart output:** `published_rag_embeddings` in the marts dataset (default var `marts_dataset: mobius_rag`), under a dbt contract with a unique test on `id`.
- **Outbound to Chat:** metadata to Chat Postgres table `published_rag_metadata`; embeddings to Vertex AI Vector Search. Contract: `docs/CONTRACT_MOBIUS_CHAT_PUBLISHED_RAG.md`.
- **Sync audit table:** BigQuery `sync_runs` (run_id, started_at, finished_at, mart_rows_read, postgres_rows_written, vector_rows_upserted, status, error_message), one row per `sync_mart_to_chat.py` run.
- **Dataset env vars other environments must set:** `BQ_PROJECT`, `BQ_DATASET`, `BQ_MARTS_MEDICAID_DATASET`, `BQ_MARTS_FINANCIAL_DATASET`; sync additionally needs `CHAT_DATABASE_URL`, `VERTEX_PROJECT`, `VERTEX_REGION`, `VERTEX_INDEX_ID`.
- **Job service HTTP surface:** `GET /config`, `POST /runs`, `GET /runs`, `GET /runs/{run_id}`, `GET /`.
- **Model names are the interface.** 148 models across `landing`, `marts/chat_rag`, `marts/medicaid_npi`, `marts/bh_roster`, `marts/financial_benchmarking`, and `marts/strategy`; anything selecting these tables by name breaks if they are renamed.

## Known gaps carried into v1.0.0
- The `medicaid_npi` mart carries a large set of positional `step*.sql` models (step1 through step13a, with lettered variants) whose names encode pipeline order rather than meaning; they are unreadable to anyone outside this repo.
- Several marts exist in both original and `_v2` form side by side (`org_kpis` / `org_kpis_v2`, `hcpcs_rate_benchmarks` / `_v2`, `peer_distributions` / `_v2`); the older versions are not deprecated or removed, so consumers must know which is current.
- The expensive marts are excluded from CI, so medicaid_npi, bh_roster, financial_benchmarking, and strategy get no automated test coverage on change — correctness there depends on manual or nightly runs.
- Sync to Chat is opt-in by environment: `land_and_dbt_run.sh` silently skips the sync step when `CHAT_DATABASE_URL` and the Vertex vars are unset, so a "successful" pipeline run does not imply downstream data moved.
- The landing table must be created out-of-band via `scripts/create_landing_table.sql` in the BigQuery console, as must `sync_runs`; neither is managed by a migration.
