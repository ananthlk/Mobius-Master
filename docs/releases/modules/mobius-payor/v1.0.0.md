# mobius-payor v1.0.0

**Commit:** `ee05685` · **Branch:** `claude/sources-module-canonical-payor-enumerate` · **History:** 280 commits, 2026-07-03 → 2026-09-07

`claude/sources-module-canonical-payor-enumerate` is the live state and sits 227 commits ahead of `main`.

## What this module is

mobius-payor is the payor platform: it establishes and tracks whether Mobius has what it needs
to support a given payor — corpus documents, operational facts, APIs, sitemap coverage — and
exposes that as a readiness registry, a document-integrity judge, and a family of
chat-callable skills. It runs as its own Cloud Run service with its own git history and shares
only the Cloud SQL `mobius_rag` database with mobius-rag.

## What v1.0.0 establishes

- A per-payor readiness pipeline driven from a seed file: `loader` → `corpus_check` →
  `sitemap_sync` → `bankgen` → `integrity_judge` → `dashboard` → `health_check`.
- A chat-exposable skills API (`app/routers/payor_skills.py`) for payor lookup, readiness, docs,
  prior-auth checks and sitemap, served under a manifest.
- Classification ownership: a per-payor rule-pack engine, authoritative-domain and robots-status
  CRUD, gate telemetry with per-gate expandable emits, and a `gate_decisions` record for every
  determination.
- Typed platform work queues — dedup, held, trust review, authority review — with drill-downs,
  bulk actions, deep links into RAG, and determinations forwarded to RAG's live executor.
- A service line registry: lines, codes, modifiers, benefits and benefit limits as structured,
  checkable facts, with a uniform response envelope, typed caveats (including blocking caveats
  that carry their choices) and a human review queue that records where a value came from.
- Deep-research integration read-side: sourcing runs that can be started, watched and replayed
  from the state machine's own provenance rows, with graded citations.
- A migration ledger of 66 numbered SQL migrations carrying the schema for all of the above.

## Notable in the run-up

- The service line registry API was hardened envelope-first: one envelope on every endpoint,
  caveats carrying a `kind` so a UI knows where to place them, `select_kind` on blocking caveats,
  jurisdiction derived rather than asserted, and 404 brought inside the envelope guarantee.
- Sourcing runs became observable and replayable — a run reads the deep-research state machine's
  provenance instead of building a second one, names the model profile it was asked under, and
  can be started from the registry's Source button.
- Citations are now graded before being rendered as evidence, with the verdict carried through
  the API; table rows stopped being graded as second-class, and held documents stopped being
  reported as missing.
- Product-line authorship was settled with RAG (coordination A-54/A-55): the contract derives
  `product_line`, RAG scribes it; CMS→CWSP and base→MMA migrated to a single spelling.
- Dedup federation with RAG landed end to end — reading RAG's duplicate groups, distinguishing
  candidates from determinations, requiring both-sides product on a pair decision, and fixing an
  append-only ledger that had been resurrecting resolved pairs.

## Known gaps carried into v1.0.0

- The live state is a feature branch, 227 commits ahead of `main`. Anything built against `main`
  is building against a materially different module.
- Two migrations share number `047` (`047_line_lexicon_d.sql` and `047_research_turns.sql`) and
  two share `050` (`050_attempt_in_flight_outcomes.sql` and `050_document_tables.sql`). The
  numbering is no longer a total order.
- The final week's commits are self-corrections on shipped code: a review pass found four faults
  in already-shipped registry code, a CORS regex matched only one subdomain level, and the
  published surface could not call the API at all. The surface is young.
- `RESTORE_REVISABLE_CHAINS` remains a feature flag defaulted to `False`; the revisable-chain
  restore stage is written but not on.
- Coverage numbers reported from the crawler sprint (39/39, 185/185, 6,744/6,744) are per-run
  verifications recorded in `docs/sprint`, not a standing guarantee about corpus completeness.
