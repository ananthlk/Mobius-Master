# mobius-db-agent v1.0.0

## What this module is
mobius-db-agent is a centralised, governed database-access service for the Mobius fleet. It runs an MCP server (FastMCP, stateless HTTP, JSON responses) exposing SQL tools that every calling service reaches through a per-service access manifest instead of holding its own database credentials. The same HTTP app also carries REST routes that provision per-org document-store namespaces in the `mobius_org_docs` database.

## What v1.0.0 establishes
- An MCP server (`app/server.py`) over four named databases — `chat`, `rag`, `user`, `qa` — with connection pools managed centrally (`app/pools.py`) under a total-pool ceiling.
- Four MCP tools: `db_query`, `db_execute`, `db_transaction`, `db_get_schema`, plus a `db_health` metrics tool.
- Manifest-based access control (`app/access.py`, `manifests/*.yml`): per-caller read/write table allowlists and per-caller `max_rows` / `timeout_seconds` limits, with statement inspection that extracts the read tables and write target from the SQL before executing it.
- A contract validator (`app/contracts.py`) that caches table schemas and validates write column sets before a statement runs.
- A structured error taxonomy (`app/errors.py`) that classifies driver and infrastructure exceptions into stable codes for callers.
- The org doc-store provisioner: `POST /doc-store/provision` (idempotent create-if-absent) and `GET /doc-store/{org_slug}`, applying a vendored org_docs DDL into a per-org PostgreSQL schema.
- A drop-in client (`db_client.py`) that consuming modules copy in, plus an integration spec describing the manifest a new caller must add.

## Contracts other modules depend on
- MCP endpoint at `/mcp` on the service (`mobius-db-agent`), default port 8008 via `DB_AGENT_PORT` or `PORT`. Tools and their calling shape: `db_query(sql, db_name, params)`, `db_execute(...)`, `db_transaction(...)`, `db_get_schema(db_name[, table])`, `db_health(caller_id)`. `db_query` returns `{"columns": [...], "rows": [...]}`.
- Caller-side env vars: `DB_AGENT_MCP_URL` and `DB_AGENT_CALLER_ID` (which must equal the `service:` field of the caller's manifest).
- Access manifests live in `manifests/<service>.yml` with `service`, `permissions.<db>.read/write` table lists (or `"*"`), and `limits.max_rows` / `limits.timeout_seconds`. Adding a table a service reads or writes requires a manifest change here.
- REST routes on the same app: `POST /doc-store/provision` with body `{org_slug, kind?, schema_version?}` returning `{namespace_ref, created, status: created|already_exists|upgraded, schema_version}`; `GET /doc-store/{org_slug}` returning the record or a `relation_missing` error with 404. Both require header `X-Internal-Key` matching `DB_AGENT_INTERNAL_KEY`. Asserting a `schema_version` newer than the vendored DDL returns 409 `schema_unavailable`.
- Database `mobius_org_docs`: one PostgreSQL schema per org slug, each containing `org_schema_version`, `org_documents`, `org_chunks` (embedding `vector(1536)`, HNSW cosine index `m=16, ef_construction=64`, GIN full-text index, unique `content_sha`). Requires the pgvector extension on the host instance.
- Service-side env vars: `DB_AGENT_CHAT_URL` / `CHAT_RAG_DATABASE_URL`, `DB_AGENT_RAG_URL` / `DATABASE_URL`, `DB_AGENT_USER_URL` / `USER_DATABASE_URL`, `DB_AGENT_QA_URL` / `QA_DATABASE_URL`, `DB_AGENT_ADMIN_URL`, `DB_AGENT_ORG_DOCS_URL`, `DB_AGENT_ORG_DOCS_SCHEMA_DIR`, `DB_AGENT_POOL_TOTAL_MAX` (default 15) and per-database `DB_AGENT_POOL_<NAME>_MAX`, `DB_AGENT_ALLOW_ADMIN`, `DB_AGENT_INTERNAL_KEY`, `USE_CLOUD_SQL_PROXY`.
- `org_docs_schema/v001_schema.sql` is vendored from mobius-rag and must not be edited here; it is re-synced with `scripts/sync_org_docs_schema.py`. RAG owns the file, so its shape is a shared contract between the two modules.

## Known gaps carried into v1.0.0
- When `DB_AGENT_INTERNAL_KEY` is unset the REST routes run unauthenticated; the code only logs a warning and continues. Any deploy that forgets the variable exposes org doc-store provisioning to anyone who can reach the service.
- The client is distributed by copying `db_client.py` into each consumer rather than as a versioned package, so client fixes must be re-copied per module and can drift.
- Access control is enforced by parsing SQL text to extract read tables and write targets; the guarantee is only as strong as that parsing, and manifests permit `"*"` wildcards.
- `DB_AGENT_ALLOW_ADMIN` enables an admin caller bypass and an admin database URL derived from the chat URL — a single env flag that removes manifest enforcement for that caller.
- The provisioner's own record is a debug read only; the integration spec states roster's `org_doc_store` registry is the system of record, so the two can disagree with nothing here to reconcile them.
- Five commits and no deploy env file in the repo: the Cloud Run configuration for this service is not captured alongside the code the way the other modules' `deploy/dev.env` is.
