# mobius-feedback v1.0.0

**Commit:** `8c3d319` · **Branch:** `main` · **History:** 1 commit (module carve-out), 2026-09-07

## What this module is
mobius-feedback is a stateless classifier service that turns a user's raw product feedback into a structured record: category, sentiment, severity, a short summary, a tidied verbatim, and a downstream routing destination. It is a FastAPI app deployed to Cloud Run as `mobius-feedback`. It stores nothing — persistence and cadence live chat-side in `mobius-chat/app/storage/product_feedback.py`.

## What v1.0.0 establishes
- A single classification endpoint, `POST /classify`, plus `GET /health`.
- A fixed taxonomy in `app/policy.py`: eight categories (`accuracy_trust`, `coverage_gap`, `bug`, `speed`, `usability`, `feature_request`, `praise`, `other`), four sentiments, three severities, with coercion functions that map any off-taxonomy model output back to a safe default.
- A routing table mapping category to destination: `triage_queue` for `accuracy_trust` and `bug`, `corpus_backlog` for `coverage_gap`, `none` for `praise`, `product_backlog` otherwise.
- Router-first LLM access: calls the chat LLM router at `{FEEDBACK_LLM_ROUTER_URL}/internal/skill-llm` under the `feedback_classify` stage, falling back to a direct Anthropic call when the router is unavailable.
- Graceful degradation — on an LLM failure, an unparseable response, or an empty verbatim, the service returns a well-formed `ClassifyResponse` with a `reason` field instead of erroring.
- PHI-in-logs compliance: on a parse failure only the output length is logged, never the model text.
- Offline unit tests (`tests/test_service.py`) that monkeypatch the LLM call, plus a Cloud Run deploy script and `deploy/dev.env`.

## Notable in the run-up
- The service mirrors the shape of `mobius-skills/vibe` — same LLM client structure, same deploy script pattern — so the carve-out did not introduce a new service idiom.
- A dedicated cheap-and-fast LLM stage, `feedback_classify`, was registered chat-side (`_SKILL_LLM_ALLOWED_STAGES` and the model registry) on 2026-07-02; this module depends on that registration.
- Output is bounded by construction: summary truncated to 160 characters, tidied verbatim to 600, response budget `FEEDBACK_MAX_TOKENS=600`.
- The response carries the router's `usage` dict straight through, so the caller sees which model actually served the classification.
- Cloud Run sizing is deliberately small: 512Mi, 1 CPU, concurrency 40, 30s timeout, max 3 instances, scale-to-zero.

## Contracts other modules depend on
- `POST /classify` request: `{verbatim: str, context_excerpt?: str, provisional_category?: str, correlation_id?: str}`.
- `POST /classify` response: `{classification: {category, sentiment, severity, summary, tidied}, routed_to, skipped, reason, usage}`. Field defaults are `category="other"`, `sentiment="neutral"`, `severity="low"`, `routed_to="product_backlog"`, `skipped=false`.
- `GET /health` returns `{"ok": true, "service": "mobius-feedback"}`.
- The category, sentiment, severity and `routed_to` enums in `app/policy.py` are the shared vocabulary; the chat-side store and any triage consumer are coupled to those exact strings.
- Upstream dependency: the chat LLM router endpoint `POST {FEEDBACK_LLM_ROUTER_URL}/internal/skill-llm`, authenticated with header `X-Mobius-Skill-LLM-Key`, and the `feedback_classify` stage being present in chat's allowed-stage list.
- Env vars: `FEEDBACK_LLM_ROUTER_URL` (or `MOBIUS_CHAT_URL`), `MOBIUS_SKILL_LLM_INTERNAL_KEY`, `FEEDBACK_USE_CHAT_LLM_ROUTER`, `FEEDBACK_LLM_STAGE`, `FEEDBACK_MAX_TOKENS`, `FEEDBACK_ANTHROPIC_MODEL`, `ANTHROPIC_API_KEY`.

## Known gaps carried into v1.0.0
- CORS is `allow_origins=["*"]` with all methods and headers, and the service has no authentication of its own — anyone who can reach the Cloud Run URL can spend LLM budget through `/classify`.
- The service is stateless by design, which means it has no record of what it classified; if the chat-side write fails, the classification is simply lost and there is nothing here to replay.
- Category assignment is a single LLM call with no evaluation set, no agreement measurement, and no drift monitoring — the coercion functions guarantee a valid enum value, not a correct one.
- The Anthropic fallback path bypasses the chat router entirely, so those calls are outside the router's model-selection and telemetry, and the fallback silently changes which model answered.
- Test coverage is one file exercising the endpoint with a stubbed LLM; the router client, the fallback path and the deploy script are untested.
- `FEEDBACK_LLM_ROUTER_URL` in `deploy/dev.env` is a hardcoded Cloud Run revision-style hostname rather than a stable alias.
