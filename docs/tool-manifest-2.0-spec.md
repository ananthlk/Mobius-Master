# `tool_manifest` 2.0 — specification

**Status: DRAFT FOR REVIEW. Written by the Platform seat, 2026-09-10.**
**Not implementation-ready until §9's sign-offs. No code has been written.**

Companion to `docs/tool-manifest-schematic.md`, which is the evidence base. Every design
choice below cites the section that measured it. Where a claim has no measurement, it
says so.

---

## 1. What this is, and what it replaces

**1.0** renders a static catalogue: all 57 tools, ~13,062 tokens, identical on every
round of every turn, narrowed only by chat mode and per-user subscription.

**2.0** is a **per-turn selector**: it chooses a ranked subset, attaches the reason each
tool was chosen, and renders only those. It is deterministic — no model in the loop — so
it can be tested with fixtures.

**It is a swap, not an edit.** 1.0 stays in the tree, untouched and callable, for the
life of the A/B and after it. Ananth, 2026-09-10: *"we can always swap it.. instead of
changing the correct and we can do a a/b."*

---

## 2. The interface — how the swap works

2.0 implements **exactly** 1.0's public surface. No caller changes.

```python
get_tool_manifest(allowed: list[str] | None = None, *, ctx=None) -> str
get_manifest_tool_names(allowed: list[str] | None = None, *, ctx=None) -> list[str]
```

- `ctx` is **new and optional**. 2.0 needs the query (and at round N, the open gaps);
  1.0 ignores it. A caller that passes nothing gets 1.0 behaviour from either
  implementation.
- **Selection is by config, resolved per turn**, not by import: `TOOL_MANIFEST_VERSION ∈
  {1, 2, shadow}`. Import-time selection cannot be A/B'd and cannot be killed without a
  deploy.
- **`get_tool_manifest` and `get_manifest_tool_names` MUST agree.** Nothing enforces that
  in 1.0 (schematic §4.4). In 2.0 the names are the *input* to the render, so agreement
  is structural rather than asserted — and a test pins it anyway.

---

## 3. 🔴 PHASE 0 — SHADOW MODE, and it is the most valuable phase

**Before any A/B, run 2.0 in shadow: compute the selection, record it, serve 1.0's
manifest.** Zero behaviour change, zero risk, and it answers the question an A/B cannot
answer cheaply.

**The metric it produces — recall against actual calls, with no labelling required:**

> For each turn, react called some set of tools **T**. Was every member of **T** present
> in 2.0's selected set?

This is a **ground truth we already have**, generated by production traffic, requiring no
golden set and no human judgement. It directly measures the only failure that matters:
**2.0 excluding a tool the turn actually needed.**

**Why this is better than an A/B first:**
- an A/B measures *outcome* (rounds, latency, answer quality) and is confounded by
  everything else in the loop
- shadow measures *the selector* in isolation, which is the thing being changed
- and it is safe: a shadow miss costs nothing, while an A/B miss costs a user's turn

**Exit criterion for Phase 0:** recall against called tools ≥ 99% over a stated window
and turn count, with every miss individually reviewed. **A miss is not a percentage
point — it is a case to read.**

Recorded per turn, bound to the schema node key per the P2b convention:

| span | payload |
|---|---|
| `tool_manifest.v2_shadow` | selected names · scores per signal · tokens · tier of each · reason |
| `tool_manifest.v2_recall` | called ∖ selected (**the misses — empty is the goal**) |

**The misses must be recorded as names, not a count.** A count of misses is
`is_fallback` (schematic §14.4 / the `blocks_assembled` lesson): it passes every
absent-producer test while telling nobody which tool was dropped.

## 4. The selector

Four stages, from schematic §8.1. Each is a pure function of declared inputs.

### Stage A — authority (hard filter, no scoring)

`caller ∩ supports_modes[mode] ∩ visible_to_planner ∩ user_tool_subscriptions`

**Authority is never a rank input** (§8.4). A high-relevance tool must not outrank its
own permission boundary. Output: the caller's eligible set.

### Stage B — `requires` (hard filter, no scoring)

Drop any tool whose declared `requires` cannot be satisfied from the query's resolved
Lexicon tags. §10: a tool that cannot function must be **excluded with a stated reason**,
not ranked low — because a low-ranked tool still surfaces on a thin turn and then gets
called without what it needs.

### Stage C — score, three signals fused by rank

| signal | measured behaviour | schematic |
|---|---|---|
| **Lexicon tag overlap** (`d:`/`p:`/`j:`) | exact on entity and domain; **silent on implied intent** | §12.2 |
| **BM25** over tool text | best on exact procedural terms; poor on short generic queries | §12.1, §14.1 |
| **vector** (`text-embedding-004`, 768-dim) | best on short generic queries; **blurs discriminating terms** | §14.1 |

**Fuse by reciprocal rank (RRF), not by weighted score.** §14.2: rank fusion avoids a
magic constant on an unnormalised scale, which §13.4 identified as a smell. k=60 as the
untuned default, and **untuned is the honest state** — anything fitted to the four
queries in the schematic is fitted, not learned.

### Stage D — admit, and render

- **tier `default`** — always present. A floor, not a competitor (§13.1).
- **tier `specific`** — admitted on clearing an absolute floor; if none clears it, **admit
  nothing specific** and serve defaults only (§13.2, the *"what is prior authorization"*
  case).
- **tier `utility`** — not domain-selected.
- **cap**: top-N specific, N budget-derived from remaining prompt space, not a constant.

Output: the ranked names, each with **the reason it was admitted** — the signal that
carried it and the tags matched. §8.4: react confirms rather than re-derives, and a
selection nobody records is a producer with no consumer.

## 5. What must be declared per tool, and what happens when it isn't

Three new `SkillSpec` fields. `SkillSpec` already spans builtins **and** MCP tools
(`source="mcp"`), so all 57 can carry them (§9.1).

| field | type | meaning |
|---|---|---|
| `tier` | `"default" \| "specific" \| "utility"` | how it is selected |
| `subscribes` | `list[str]` | Lexicon tags it is relevant to → contributes to score |
| `requires` | `list[str]` | tags that must resolve or it is **ineligible** |

**🔴 A tool with no declaration must FAIL LOUDLY, not default silently.** An undeclared
tool defaulting to `tier="specific"` with empty `subscribes` becomes permanently
unselectable and *invisible* — no error, no log, just a tool never offered again. That is
`make_tool_failed` exactly (schematic §10.3). **Startup must refuse to register a
planner-visible tool with no `tier`.**

**And a tag declared against a retired Lexicon axis must fail a build**, not silently
never match — same reason, same shape as the mutation ledger's decay rule (§10.3).

**Ownership:** the 29 MCP tools' declarations are a contract question with the team that
publishes them (§10.4 q2). Either the MCP server declares them in `list_tools`, or chat
maintains an override table. **Unresolved, and it blocks full coverage** — though not
Phase 0, since undeclared tools can be treated as `default` in shadow and the recall
metric will show what that costs.

## 6. Failure behaviour — and one place I am contradicting my own habit

**If 2.0 raises, times out, or selects an empty set: serve 1.0's full manifest.**

That is **fail-open**, and I have spent this program arguing for fail-closed. The
distinction is deliberate and worth stating:

- a **gate** decides whether something is *allowed*. Fail-closed: the cost of wrongly
  proceeding exceeds the cost of wrongly blocking. (The PHI gate.)
- a **selector** decides what is *offered*. Its worst failure mode is **today's
  behaviour** — all 57 tools. Fail-closed here would mean serving *no* tools, which
  breaks every turn to protect against a token bill.

**So: fail open, but count it.** A `tool_manifest.v2_fallback` span with the reason, and
**an alert if the rate is non-trivial** — because a selector that silently falls back on
every turn is indistinguishable from one that was never enabled, and that is the exact
shape this program keeps finding.

**Kill switch:** `TOOL_MANIFEST_VERSION=1` must take effect **without a deploy**.

## 7. Phasing

| phase | what runs | exit criterion |
|---|---|---|
| **0 — shadow** | 2.0 computes, 1.0 serves | recall vs called tools ≥ 99%, **every miss read individually** |
| **1 — A/B** | 2.0 serves a % of turns | no regression in rounds-to-answer or `no_sources` rate; manifest tokens down; **selection recall holds** |
| **2 — default** | 2.0 serves, 1.0 retained | 1.0 stays callable for one full cycle after |
| **3 — round N** | gaps + tried-tools feed Stage C | **deliberately last** — see below |

**Round-N is phased last, and that is a change from where the design started.** §11.2 and
§13.3 concluded that Ananth's CARC 197 turn is a **round-N failure, not a ranking
failure**: the loop called one tool, got `no_sources` twice, held the same two gaps for
three rounds, and never tried the sibling that was in the manifest. So round-N is the
higher-value half — but it depends on `tool.result` history that only began existing
2026-09-10, and on the governor's gap state being **stale by one round by construction**
(§8.4 constraint 5). **Phase it last because it is the most valuable and the least
grounded, not because it is optional.**

## 8. What 2.0 explicitly does NOT do

- **does not dispatch.** Still `react_loop`. A tool being selected is not evidence it works.
- **does not fix the descriptions.** §15 measured a 72% reduction and a ranking improvement
  from cleaning the appeals prose, and that is a **separate, independently valuable
  change** owned by whoever owns each tool's semantics. 2.0 must improve things over the
  *current* prose, or it is depending on a rewrite it does not control.
- **does not delete the 29 unused MCP tools.** Chat Master measured **zero emissions
  across the entire recorded window** (§3.1), and their own caveat stands: the window was
  appeals traffic and these are market analytics. That is a catalogue decision on evidence
  we do not yet have.
- **does not judge answer quality.** Out of scope, and Eval's ruling on the invariant set
  already excludes it.

## 9. Open, and who owns each

| # | question | owner |
|---|---|---|
| 1 | `tier` / `subscribes` / `requires` for the 28 static tools | tool semantics owners |
| 2 | same for the 29 MCP tools — server-declared or chat override? | contract with the MCP team |
| 3 | the golden set: who owns it, how many fixtures before the ranker is trusted | **unowned — the real prerequisite** |
| 4 | absolute floor and top-N: normalised how? | implementer, with §13.4's warning |
| 5 | re-embed on description change — who triggers it? | drift owner; §14.4 |
| 6 | do the 29 market tools dispatch at all | one turn, and it halves the catalogue either way |

**Question 3 is the one that gates everything.** A deterministic selector with no ground
truth is *reproducibly* wrong (§8.4 constraint 2). Phase 0's recall metric is a partial
substitute — it uses production calls as labels — but it can only tell us 2.0 dropped a
tool react wanted. It cannot tell us **react wanted the wrong tool**, which is the actual
CARC 197 failure.
